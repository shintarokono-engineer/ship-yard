# ADR-015: 無料公開アイデア検証ツールによる初期ユーザー獲得

## ステータス

承認済み(2026-08-30)

## 背景・問題

2026-08-04 に本番公開したが、**LP への訪問自体がほぼ 0** で初期ユーザーを獲得できていない。PostHog の CTA / pricing 計測は実装済みのため、これは訴求(訪問はあるが登録されない)や動線(登録はされるが機能に到達しない)の問題ではなく、**流入そのものが存在しない**問題であると特定した。

### 解決すべき設計課題

1. **訴求の焦点**: 9 系統に広がった機能のうち、何を強みとして名乗るか
2. **流入の作り方**: 検索・共有される接点を Neorie がまったく持っていない
3. **体験の壁**: 全機能がログインの背後にあり、価値を 1 度も見せられない
4. **無料開放の費用**: ログイン不要で AI を叩かせた場合の実費と、その天井の保証方法
5. **無料版と有料版の関係**: 何を無料にし、何を課金理由として残すか

### 現状認識

- **機能が薄く広い**: `CHECKLIST` / `RAG_QA` / `ANNOUNCEMENT` / `LANDING_PAGE` / `IDEA_VALIDATION` / `PRODUCT_DIAGNOSIS` / README / ブログ / タスク分割の 9 系統。プロジェクト詳細で 6 枚のカードが等価に並び、「まず何をすべきか」をプロダクトが示していない
- **訴求が説明を要する**: LP の「アイデアからリリースまで、一直線に」は **誰も検索しない語**。「アイデア 評価」「ビジネスアイデア 採点 AI」のような実際に打たれるクエリと一致する接点が無い
- **初回体験までが遠い**: サインアップから初回のアイデア検証まで 6 ステップ、命名判断 2 回、フォーム 3 枚、最後に 6 択
- **`IDEA_VALIDATION` に直行導線が無い**: §9.7 で実装した `NewProjectDialog` の「AI と壁打ち」モードは `/rag-qa` に飛ぶ。アイデア段階のユーザーが最初に触るべき検証機能には、どこからも直行できない

### コストの実態(F23、2026-08-29 実測)

`IDEA_VALIDATION` / `PRODUCT_DIAGNOSIS` は 1 回 **¥41.65**(6cr / ¥6.94 per cr)。Pro の損益分岐 ¥4.93/cr を上回る。内訳は以下で、**コストの約 90% を Web Search が生む入力トークンが占める**。

| 内訳                                           | 概算                            |
| ---------------------------------------------- | ------------------------------- |
| 入力 67,831 tok × $3/MTok(`claude-sonnet-4-6`) | ¥30.5                           |
| 出力 約 2,000 tok × $15/MTok                   | ¥4.5                            |
| Web Search 5 回 × $0.01                        | ¥7.5                            |
| **合計**                                       | **≒ ¥42.5**(実測 ¥41.65 と整合) |

関連: ADR-003(テナント解決、`/w/{slug}` の共有性)、ADR-005(AI 戦略)、ADR-012(プラン構造、Free 廃止 + 7 日トライアル)、ADR-013(2 モード化、`IDEA_VALIDATION` の rubric)、**ADR-016(rubric を実質評価へ改訂。本 ADR の前提)**、PROJECT_STATUS §9.9 / §9.12.2 F23

## 検討した選択肢

### A. 公開アイデア検証ツール(ログイン不要)

- 概要: `neorie.com/check` を無ログインで公開。アイデアを 1 フォームに書くと、検索を伴わない 3 軸で採点し、改善提案を返す。結果から Neorie の登録へ繋ぐ
- 長所:
  - **単機能として名乗れる**ため、「アイデア 評価」等の検索意図と一致する接点が生まれる。現在の Neorie がまったく持っていない性質
  - **説明が不要**。「アイデアからリリースまで一元管理」は説明を要するが「アイデアを採点します」は要さない。薄く広い 9 機能を 1 つの入口に畳める
  - 口コミで人に一言で説明できる(説明可能性)
  - 既存の `idea-validation` モジュール(rubric / 3 段防御 / 結果表示コンポーネント)を高い比率で再利用できる
  - ロックした 2 軸がその場に見えるため、アップグレード導線が具体になる
- 短所:
  - ログイン不要の LLM エンドポイントは**費用を燃やす攻撃対象**になる
  - 検索経由の流入が立ち上がるまで数か月かかる(ドメイン権威が無い)ため、**初期ユーザー獲得を単独では担えない**
  - Web Search を外すため 5 軸のうち 2 軸が評価できない

### B. 公開 LP ギャラリー

- 概要: 既に実装済みの `/p/{slug}/{projectId}` 公開 LP の一覧ページを作り、各 LP に "Made with Neorie" を置く。ユーザーが増えるほど被リンクと流入が増える
- 長所: 実装が軽い。ユーザー数に対して流入が線形以上に伸びる
- 短所: **ユーザーが 0 の現在は 1 件も並ばない**。鶏卵問題により初速がまったく出ない

### C. 技術記事による流入(Zenn / X)

- 概要: 「Sonnet + Web Search + Tool Use で構造化スコアを実装する設計判断」等を Zenn に書く。ADR-013 がほぼそのまま原稿になる
- 長所: **日本の個人開発者の生息地に直接届く**。ドメイン権威に依存せず、公開初日から流入が発生しうる
- 短所: 単発で減衰する。記事単体では継続的な流入資産にならない

### D. 現状維持(ログイン必須のまま LP のコピーを改善)

- 概要: 機能構成は変えず、LP の訴求文を「アイデア検証」中心に書き換える
- 長所: 実装コストがほぼゼロ
- 短所: **訪問が 0 である以上、訪問後の訴求を変えても効果が測れない**。問題の所在を取り違えている

## 決定

**A を採用し、C を点火装置として併走させる。B は有料ユーザーが発生してから再評価する。**

当初 A 単独を採用しかけたが、これは B を「鶏卵問題があるので不採用」とした基準を A に適用していない誤りだった。**A も同じドメイン上の新規ページであり、それ自体は最初の 1 周を回さない。** A が持つ検索接点は数か月かけて育つ資産であり、初期の数十〜百人は C が connect する。両者は競合ではなく時間軸が異なる。

### A の具体構成

| 項目               | 決定                                                                                                                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| URL                | `/check`(ログイン不要、Clerk middleware から除外)                                                                                                                                            |
| 評価軸             | **3 軸**(`problemClarity` = 課題の強度 / `targetClarity` = 対象の到達可能性 / `differentiation` = 打ち手の妥当性。ラベルは ADR-016)。`competitiveAdvantage` / `marketPotential` はロック表示 |
| スコア名           | **「アイデア検証スコア」**(有料版と同一名称)、**100 点満点**                                                                                                                                 |
| 採点方式           | 内部は 3 軸 × 20 点 = 60 点で採点し、**表示時に 5/3 倍して 100 点満点へ正規化**。rubric は **ADR-016 で実質評価に改訂したもの**を使う                                                        |
| 出力の主役         | **改善提案**。スコアは併記                                                                                                                                                                   |
| GO / PIVOT / NO_GO | **出さない**                                                                                                                                                                                 |
| モデル             | `AI_MODEL_HAIKU`(現行 `claude-haiku-4-5-20251001`、版固定運用)、**Web Search なし**                                                                                                          |
| 費用の天井         | **日次のグローバル上限**で保証。IP 制限は補助                                                                                                                                                |
| 結果 URL           | 推測不能 ID + 既定 `noindex`。共有は opt-in                                                                                                                                                  |
| 登録への接続       | 結果 ID を短命トークンで持ち越し、ワークスペース / プロジェクト / 5 軸フル診断を自動生成                                                                                                     |

### Web Search を外す軸の切り分け

`VALIDATION_AXIS_RUBRIC` を検索依存で分けた結果に基づく。

| 軸               | 検索なしでの精度                                                                  | 無料版   |
| ---------------- | --------------------------------------------------------------------------------- | -------- |
| 問題明確性       | 変わらない(記述の具体性を rubric で採点するだけ)                                  | 採点する |
| ターゲット明確性 | 変わらない                                                                        | 採点する |
| 差別化           | ほぼ変わらない(差別化軸の言語化を見る軸で、競合の実在性は問うていない)            | 採点する |
| 競合優位性       | **大きく落ちる**(rubric に「Web Search で取得した実競合と比較して」と明記)        | ロック   |
| 市場性           | **大きく落ちる**(rubric に「取得した競合数 / 投資情報 / トレンドから推定」と明記) | ロック   |

`competitiveAdvantage` の rubric には「Web Search 無効時は LLM の事前学習知識ベースで評価(精度低下を UI で明示)」というフォールバックが既に記述されているが、**本 ADR ではこれを採らず非表示とする**。精度低下を注記しても、点数が存在する限り読者は点数を信じるため。

GO / PIVOT / NO_GO を出さないのも同じ理由による。`VALIDATION_RECOMMENDATION_GUIDANCE` は **PIVOT の条件に「競合優位性 10 点未満」を直接使っている**ため、検索なしでは最も目立つ結論が当てにならない根拠で決まる。

## 理由

- **流入 0 は訴求の問題ではなく接点の問題**。単機能ツールとして名乗ることでのみ、検索されうる語と一致する接点が生まれる。D はこの取り違えを温存する
- **A は 9 機能を削らずに畳める**。機能統廃合という破壊的変更を伴わず、入口を 1 つに絞ることで「薄く広い」問題に対処できる
- **同一名称 + 事前開示を採る根拠**: 当初は無料版を「アイデア言語化スコア」と別名にする案だったが、これは採点対象がアイデアから文章にすり替わって見え、**確立したばかりの検索意図との一致を自ら壊す**。二重名称の動機だった「有料で点が下がると裏切られたと感じる」への対処は、開示で足りる。反対していたのは点の低下ではなく不意打ちであり、開示で解ける問題にブランド分割という重い手を当てていた
- **正規化(3 軸 → 100 点)を採る根拠**: 「100 点満点の 60 点分だけ採点し 40 点分を未判定とする」案は尺度が 1 つで矛盾せず課金圧も強いが、初見の訪問者に減点表示の印象を与え共有されにくい。**現在の課題は転換率ではなく流入**であるため、共有されやすさを優先する。正規化そのものは表示層の変更だけで済み、`validation-schema.ts` の整合性アサートは無改修で通る
- **トレードオフの受容**: 3 軸のみの 100 点満点は、最も辛い 2 軸が不在であるため**構造的に甘い点数**になる。これは信頼性を共有されやすさと引き換えにする意図的な判断であり、ロック 2 軸の明示と「追加するとスコアは変動します」の開示で誠実さを担保する
- **B の棄却**: 鶏卵問題。ユーザーが 0 の現在は 1 件も並ばない。有料ユーザーが発生してから再評価する
- **C の位置づけ変更**: 当初「単発だから弱い」として補助扱いにしたが、A の検索流入が立ち上がるまでの数か月を埋めるのは C しかない。**C 抜きの A は立ち上がりが数か月遅れる**

## 結果(Consequences)

### 良い影響

- Neorie が**検索されうる語**での接点を初めて持つ
- 価値の提示にログインが不要になり、初回体験までの 6 ステップが `/check` 経由では実質 1 ステップになる
- ロック 2 軸により、Pro の課金理由が「もっと使いたければ」ではなく**画面上の空欄が埋まる**という具体になる
- 結果の持ち越しにより、サインアップ後に最初に見る画面が空のダッシュボードではなく**自分のアイデアの診断結果**になる
- `idea-validation` モジュールの再利用率が高く、新規実装は無ログイン用 controller / レート制限 / 公開結果ページ / OG 画像に限定される

### 悪い影響・リスク

- **費用の攻撃面が増える**。ログイン不要の LLM エンドポイントは濫用対象になる。日次グローバル上限をコードで保証してから公開しない限り、想定費用は無意味
- **無料版の実費 ¥2.4 / 回は未計測の推定値**。F23 自身が「現状サンプル 1 件」「着手前に数件実行して実費のばらつきを確認すること」と警告しており、これは無料版の見積もりにも適用される
- **3 軸 100 点満点は構造的に甘い**。無料 80 点 → 有料 55 点のような差が常態化する
- **rubric は「厳しく採点」を明示している**(ADR-013 の LLM スコア対策)ため、初見ユーザーの点が低く出て共有されない可能性が残る。最も辛い 2 軸を外したことで**軽減されたが解消はしていない**。出力の主役を改善提案に置くのはこの残存リスクへの対処
- 結果ページを index させると、**他人の未公開アイデアの露出**と**薄いコンテンツの大量生成による評価低下**の 2 つが起きる。既定 `noindex` はこれを避けるが、同時に「ページ数を増やして SEO 資産にする」期待も捨てる
- 検索流入の立ち上がりは数か月単位であり、**本 ADR 単独では初期ユーザー獲得の期限にコミットできない**

### フォローアップ

- **本 ADR より先に ADR-016 を実装する**。当初「既存 rubric を無改修で流用できる」としていたが誤りだった。現行の `VALIDATION_AXIS_RUBRIC` は 3 軸すべてが「〜が言語化されているか」を基準としており、**無料版が採用する 3 軸はそのままでは実質評価を 1 つも含まない**(残る 2 軸が Web Search 依存のため)。ユーザーが本番で症状を確認済みで、ADR-016 として rubric を実質評価へ改める。`/check` はこの rubric の上に建つため、先に直さないと同じ欠陥を新機能に複製する
- **実装前に必須**: 現行 `IDEA_VALIDATION` を Web Search なしで数回実行し、入力 / 出力トークン量を実測する。推定 ¥2.4 が妥当かを確認してから日次上限値を決める
- **成功条件と撤退条件が未定**。何が何日以内にどうなれば A が機能したと言えるかを別途決める。これが無いと、効かなかったときに次の機能を作り足すことになる(本 ADR の出発点そのもの)
- **サインアップ後の動線改善は流入確認後**に着手する。流入が 0 の状態でファネルの後半を磨いても回収できない。対象は (1) ワークスペース作成ステップの自動化、(2) プロジェクト詳細を `Project.status` 駆動の「次の一手」に再構成、(3) `NewProjectDialog` に検証モードを追加、の 3 件
- **(1) は ADR-003 と衝突する**。ADR-003 が `/w/{slug}` を採用した理由は「URL 共有時の摩擦を最小化」であり、`user-a3f9` のような自動生成 slug はこの根拠を無効化する。ワークスペース名だけ聞いて slug を自動導出する中間案のほうが整合する。また §9.5 の「slug 変更による公開 LP の link 切れ」にも直結する
- **(2) は今が好機**。ユーザーがほぼ 0 の現在は破壊的変更のコストが最小であり、F23 の「公開後に変えると既存ユーザーの体験が変わるため、トライアル 0 件の今のうちが望ましい」と同じ論理が当てはまる
- **本 ADR と独立して効く F23 の打ち手**(有料側の赤字解消):
  - `AI_MODEL_SONNET` を `claude-sonnet-4-6` → `claude-sonnet-5` に変更。単価が $3/$15 → **$2/$10** に下がり、同一トークン量で **¥41.65 → 約 ¥31**(-25%)
  - `WEB_SEARCH_TOOL_TYPE` の再検討。`ai.constants.ts:262-268` は「`web_search_20260209`(動的フィルタリング対応)は code_execution tool の有効化が必須」としているが、**この前提は現在は正しくない**。`web_search_20260209` は code_execution を内部で実行するため `tools` への別途宣言は不要(むしろ宣言すると実行環境が二重になる)で、対応モデルは Opus 4.6 以降 / Sonnet 4.6 以降。現行の `claude-sonnet-4-6` は該当する。動的フィルタリングは 67,831 トークンへの膨張を抑えるための機能であり、**F23 の本命**
  - 上記 2 つと `WEB_SEARCH_MAX_USES` の 5 → 2 への削減で、損益分岐 ¥4.93/cr を割る見込み
- **監視すべき指標**: `/check` の日次実行回数と上限到達率、実費の実測値とばらつき、`/check` → サインアップ の転換率、検索流入の推移(数か月スパン)
- **見直しトリガー**: 日次上限に恒常的に到達する / 実測実費が推定の 2 倍を超える / C による点火後も `/check` の実行が伸びない
