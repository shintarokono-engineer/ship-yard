# ADR-016: 評価 rubric を「記述の巧拙」から「内容の実質」へ改める

## ステータス

承認済み(2026-08-30)/ **実装・実測完了(2026-08-30)**

## 背景・問題

2026-08-30、ADR-015(無料公開アイデア検証ツール)の設計中に、出力する改善提案が「アイデアの評価」ではなく**文章の添削**として読めることが判明した。**ユーザーが本番の既存機能を実行して同じ症状を確認済み**であり、仮説ではなく出荷済みの欠陥である。

ADR-013 は `PRODUCT_DIAGNOSIS` を「公開時の差別化価値」と位置づけたが、その機能自体がこの症状を抱えている。

### 原因

rubric の評価基準が、**評価対象を「記述されている内容」ではなく「記述そのもの」に向けている**。

```
problemClarity: 「解こうとしている課題が具体的に言語化されているか」
targetClarity:  「想定ユーザーが具体的に言語化されているか」
differentiation:「差別化軸が明確に言語化されているか」
```

加えて `Suggestion.axis` は必須フィールドで、改善提案は必ずいずれかの軸に紐づく。**言語化を測る軸に紐づけて提案を生成させれば、出力は構造的に「書き方を直せ」にしかならない。** 文言の選択ミスではなく、rubric の設計に起因する必然の結果である。

さらに、両 service の `## 採点ポリシー(厳格性確保)` は「安易に高得点を付けない」という**厳しさの指示だけ**で、**何を採点対象とするかを一切指示していない**。rubric の記述がそのまま採点対象の定義として作用している。

### 該当範囲

| 機能              | 軸                                         | 現行の基準                                            | 判定          |
| ----------------- | ------------------------------------------ | ----------------------------------------------------- | ------------- |
| IDEA_VALIDATION   | `problemClarity`                           | 「具体的に**言語化**されているか」                    | ❌ 記述の評価 |
| IDEA_VALIDATION   | `targetClarity`                            | 「具体的に**言語化**されているか」                    | ❌ 記述の評価 |
| IDEA_VALIDATION   | `differentiation`                          | 「差別化軸が明確に**言語化**されているか」            | ❌ 記述の評価 |
| PRODUCT_DIAGNOSIS | `differentiation`                          | 「理由が**言語化**されているか」                      | ❌ 記述の評価 |
| PRODUCT_DIAGNOSIS | `targetClarity`                            | 「README / LP で**言語化**されているか」              | ❌ 記述の評価 |
| PRODUCT_DIAGNOSIS | `featureCompleteness`                      | 「コア機能の網羅性 + **ChecklistItem の完了率**」     | ✅ 実データ   |
| PRODUCT_DIAGNOSIS | `releaseReadiness`                         | 「法務 / 課金 / ドキュメント。**LP の publishedAt**」 | ✅ 実データ   |
| 両方              | `competitiveAdvantage` / `marketPotential` | Web Search 取得の実競合と比較                         | ✅ 実質       |

**アイデア検証のほうが重い。**5 軸中 3 軸が記述の評価で、残る 2 軸は Web Search 依存のため、**検索が効かない場面では実質評価が実質ゼロになる**。ADR-015 が無料版で 3 軸のみを採用する構成は、この状態のままでは実質評価を 1 つも含まないことになる。

### 壊れていない 2 軸が示す修正方針

`featureCompleteness` / `releaseReadiness` だけが記述の評価になっていない。理由は明快で、**採点対象が文章ではなく実データ**(`ChecklistItem` の DONE 比率、`LandingPage.publishedAt` の有無)だからである。正しい基準の作り方は 2 通りしかない。

1. **証拠を見る** — 診断側で有効。既にこの 2 軸が実践している
2. **実質を問う** — 検証側はこちら。`ChecklistItem` も `publishedAt` も存在せず、入力は Project のテキスト欄のみのため、証拠が取れない

アイデア検証で 1 を採れないことは制約だが、**「よく書けているか」ではなく「書かれている内容は成り立つか」を問う**基準にすれば 2 で成立する。文章について考えることと、文章が指している対象について考えることは別である。

関連:**ADR-013(本 ADR が rubric 節を改訂する)**、ADR-015(無料公開ツール、本 ADR に依存)、ADR-005(AI 戦略)

## 検討した選択肢

### A. rubric の `criteria` と `label` を書き換え、採点ポリシーに評価対象を明示する

- 概要:該当 5 軸の `criteria` を実質評価の基準に書き換え、`label` を対応する名前に変える。両 service の `## 採点ポリシー` に「記述の巧拙ではなく内容の実質を評価する」旨を明示する。**軸のキー(enum 値)は変更しない**
- 長所:
  - 変更が**定数ファイルとプロンプト文字列に限定**され、ロジック変更を伴わない
  - `validation-schema.ts` / `diagnosis-schema.ts` の 3 段防御、表示コンポーネント、`Suggestion.axis` の紐付けがすべてそのまま機能する
  - キーを変えないため、**既存の `IdeaValidation.breakdown` / `ServiceScore.breakdown` / `Suggestion.axis` が引き続き読める**(過去レコードの表示ラベルだけが新名称に変わる)
  - 2 機能に同時に効く
- 短所:
  - 採点基準が変わるため、**過去のスコアと新しいスコアは直接比較できない**。ADR-013 が重視した「履歴比較で前回比 ±N を見る」の連続性が一度切れる

### B. 採点ポリシーへの指示追加のみ(rubric は据え置き)

- 概要:`criteria` は変えず、system prompt に「文章ではなく内容を評価せよ」と指示する
- 長所:変更が最小。過去スコアとの比較可能性が保たれる
- 短所:
  - **rubric と指示が矛盾する**。`criteria` に「言語化されているか」と書いたまま「言語化を見るな」と指示することになり、LLM の出力は不安定になる
  - rubric は ADR-013 が「LLM スコアの限界対策」の筆頭に挙げた再現性の担保手段であり、そこに矛盾を残すのは本末転倒

### C. 評価軸の全面再設計(軸数・構成から見直す)

- 概要:5 軸という構成自体を白紙にし、アイデア段階とリリース後で最適な軸を組み直す
- 長所:最も筋の良い軸集合に到達しうる
- 短所:
  - schema / 型 / 表示 / 履歴のすべてに波及し、**ADR-015 の着手が大きく遅れる**
  - 現行の軸構成そのものに問題があるという証拠はない。**問題は軸の名前ではなく基準の向き**であり、C は過剰

### D. 現状維持

- 概要:ADR-015 の無料版でのみ実質評価の基準を用意し、既存機能は触らない
- 長所:出荷済み機能に手を入れない
- 短所:
  - **出荷済みの差別化機能が作文添削を返し続ける**
  - 無料版と有料版で基準が乖離し、「2 軸を足すとスコアが変わる」という ADR-015 の約束が破綻する
  - 同じ欠陥を新機能に複製することになる

## 決定

**A を採用する。**

### 軸の再定義(キーは変更しない)

| 機能              | キー(不変)        | 現 label         | 新 label             | 新しい基準の要旨                                                                           |
| ----------------- | ----------------- | ---------------- | -------------------- | ------------------------------------------------------------------------------------------ |
| IDEA_VALIDATION   | `problemClarity`  | 問題明確性       | **課題の強度**       | その課題は実在し、対象者にとって痛いか                                                     |
| IDEA_VALIDATION   | `targetClarity`   | ターゲット明確性 | **対象の到達可能性** | その人たちは実在し、到達でき、払う余地があるか                                             |
| IDEA_VALIDATION   | `differentiation` | 差別化           | **打ち手の妥当性**   | その解き方は課題に効くか、既存の代替で足りてしまわないか                                   |
| PRODUCT_DIAGNOSIS | `differentiation` | 差別化           | **差別化の実効性**   | 異なる特徴が機能として実在し、それを理由に選ばれるか。訴求文にあるだけの差別化は評価しない |
| PRODUCT_DIAGNOSIS | `targetClarity`   | ターゲット明確性 | **対象の到達可能性** | 想定ユーザーが実在し、到達経路があり、払う余地があるか                                     |

`featureCompleteness` / `releaseReadiness` / `competitiveAdvantage` / `marketPotential` は変更しない。

### 採点ポリシーへの追加(両 service 共通)

現行の `## 採点ポリシー(厳格性確保)` に次を追加する。

> 記述の巧拙ではなく、記述されている**内容の実質**を評価してください。記述が薄く実質を判断できない場合は、文章を採点せず「判断材料が不足している」として低く付け、**何を書けば判断できるか**を提案に書いてください。

言語化の質を見なくなるわけではない。**実質を判断できるだけの材料が無いことを、低い点と具体的な要求として返す**ことで、ユーザーの次の一手は従来と変わらない。

### `IDEA_VALIDATION` への出力追加

軸に紐づかない出力として **「先に確かめるべきこと」**(検証すべき前提、3〜5 件)を tool schema に追加する。Lean Startup の実務は前提の洗い出しから始まるため、`IDEA_VALIDATION` の位置づけ(Problem-Solution Fit 検証)と整合する。`PRODUCT_DIAGNOSIS` には追加しない(既にリリース済みのプロダクトが対象で、前提は検証済みか既に外れているため)。

## 理由

- **問題は軸の構成ではなく基準の向き**である。`featureCompleteness` / `releaseReadiness` が同じ 5 軸構成の中で正しく機能している事実が、軸そのものは妥当であることを示している。C(全面再設計)は過剰
- **B は矛盾を作る**。rubric は ADR-013 が再現性担保の筆頭手段と位置づけたものであり、そこに「言語化されているか」と書いたまま逆の指示を重ねるのは、対策の意図を無効化する
- **キーを変えないことが安さの source**。表示ラベルと基準文だけの変更で、schema・型・3 段防御・表示・既存レコードのすべてが無傷で通る
- **Web Search なしでも実質評価は成立する**。最も効く指摘は**内部整合の矛盾**(対象と収益モデルが噛み合わない、行動変容を前提にしている、価値が単一の技術精度に全依存している)であり、外部データを必要としない。実在の競合との比較だけが検索を要するため、`competitiveAdvantage` / `marketPotential` をロックしたままにする ADR-015 の構成と矛盾しない
- **トレードオフの受容**:過去スコアとの比較可能性を失うが、**比較できる過去スコアが作文の点数である以上、保存する価値がない**。ユーザーがほぼ 0 の現在は履歴の蓄積も最小で、切り替えるなら今が最も安い

## 実装と実測(2026-08-30)

同一プロジェクト(`cmr7kx5gx000b2q7dd3ts2jl6`「ボードゲーム作成」)で 5 回実行して確認した。
`AIUsage` に turn 別内訳が無かったため `ai/shared/turn-usage-log.ts` を追加して計測している。

### rubric 改訂の効果 — 目的を達成

| 軸              | 改訂前の提案                                     | 改訂後の提案                                                                        |
| --------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------- |
| targetClarity   | ターゲットユーザーの課題を**3 点以上言語化する** | ゲームマーケット来場者への**リーチ戦略の具体化**(試遊台・SNS 告知・connpass / Zenn) |
| differentiation | 理由を 1 文で定義し **LP 冒頭に配置**            | 先行作品との具体的な差別化ポイント                                                  |

breakdown の comment にも新基準が現れた。「差別化が**訴求文の記述に留まっている**」「実装・体験として確認できる材料がないため評価できない」は、新 criteria がそのまま作用した結果。採点ポリシーに足した「判断材料が不足している」 の挙動も確認できた。

**残課題**: differentiation の提案タイトルに「言語化」 が残るケースがある(本文は実質的)。この軸だけ criteria の追い込みが要る。

### スコア断絶が実出力に現れた

採点基準が変わったにもかかわらず、LLM は履歴を**連続した尺度として**「前回(6 点)から改善されている」 と比較していた。本 ADR が予告した断絶が実際に起きている。UI での注記は未対応。

### コスト構造の是正

**turn 別の実測でコストの所在が判明した。**当初「turn 2 の再送が主因」 と見立てていたが誤りで、**turn 1 の内部検索ループが 63%** を占めていた(Web Search は 1 回検索するたび、それまでの結果を積んでモデルに再入力される)。

```
turn1(in=44,383 out=2,068)  ← 63%
turn2(in=25,762 out=3,510)
turn1.content: web_search_tool_result 64,838ch / text 7,506ch
```

これを踏まえて 2 つ入れた。

1. **turn 1 を Haiku に**(`AI_MODEL_HAIKU`)。turn 1 は検索と要約のみで採点しないため質に影響しない。トークンの 63% が乗る turn を $3/$15 → $1/$5 にするのが最大の削減
2. **turn 2 へ turn 1 の最終テキストだけ渡す**(`extractTextContent`)。`turn1.content` をそのまま渡すと `web_search_tool_result`(64,838 文字)まで再送される。turn 1 の system prompt が既に「名前 / URL / 概要 / 類似性を箇条書きで」 とまとめさせているため情報は失われない

|                             | 変更前    | 変更後              |
| --------------------------- | --------- | ------------------- |
| turn2 入力                  | 25,762    | **7,564**(-71%)     |
| 合計入力                    | 70,145    | 60,810              |
| `costJpy`                   | ¥44.12    | **¥20.35**(-54%)    |
| 実費(検索料金 ¥7.5 込)      | ¥50.1     | **¥27.8**(-45%)     |
| 所要時間                    | 110 秒    | 88 秒               |
| totalScore / competitorRefs | 41 / 4 件 | 41 / 4 件(変化なし) |

`costJpy` はモデル混在で不正確になるため `sumCostJpy` を追加した(行の model = Sonnet だけで見積もると turn 1 まで Sonnet 単価になり、実費を 4 割過大に記録する)。

### クレジット価格をモデル式から切り離した

**実費を下げただけでは支出は減らない。**クレジットは `MODEL_CREDITS[model] × turnCount` で自動計算されるため、turn 1 を Haiku にすると 6cr → 4cr に下がり、Pro の 300cr で回せる回数が 50 → 75 に増えて**削減分が回数増で相殺される**。支出の天井を決めているのは実費ではなくクレジット価格である。

`FEATURE_CREDIT_OVERRIDES` に `PRODUCT_DIAGNOSIS: 5` / `IDEA_VALIDATION: 5` を追加(× `turnCount` 2 = **10cr**)。ADR-012 が用意した機構をそのまま使っており、プラン構造の変更ではない。

|            | 実費/回   | cr     | 300cr で  | 最悪支出 | 単価         |
| ---------- | --------- | ------ | --------- | -------- | ------------ |
| 変更前     | ¥50.1     | 6      | 50 回     | ¥2,505   | ¥8.35/cr     |
| **変更後** | **¥27.8** | **10** | **30 回** | **¥834** | **¥2.78/cr** |

F23 が基準としていた **¥4.93/cr(= ¥1,480 ÷ 300cr)は甘い**。売上を全額 AI に使う前提であり、Stripe(約 ¥53)とインフラ(月 $38 の頭割り、10 ユーザーなら ¥570)を引くと初期は実質 ¥3/cr 前後が上限。¥2.78/cr はこれを下回る。

**プラン上限を 300 → 200 に下げる案は採らなかった。**(1) LP の料金セクション 3 箇所に「AI クレジット 300」 と明記済みで、公開済みのダウングレードになる、(2) 診断は ¥4.43/cr、Haiku 系機能は ¥0.93/cr(F17 実測)と 4.8 倍の開きがあり、プール全体を削ると安い機能まで一律に減る。高い機能に値段を付けるのが筋。

10cr 化により `PRODUCT_DIAGNOSIS_MAX_PER_MONTH_PRO = 50` は到達不能になった(300 ÷ 10 = 30 回で先に頭打ち)。二重の歯止めとして残置している。

### `web_search_20260209`(動的フィルタリング)は不採用

コスト削減を狙って切り替えたが**逆に悪化した**ため revert した。

|          | 20250305   | 20260209           |
| -------- | ---------- | ------------------ |
| tokensIn | 67,831     | **141,632**(+109%) |
| costJpy  | ¥41.65     | **¥79.03**(+90%)   |
| 所要時間 | 53〜113 秒 | **153 秒**         |

原因は 2-step 構成との相性。turn 2 が turn 1 を丸ごと再送するため、動的フィルタリングが内部の code execution で増やしたブロックが二重に乗り、節約分を再送が食い潰す。さらに 153 秒は FE の `API_TIMEOUT_MS = 55_000` を超えるため **UI からは 504 で失敗する**。再挑戦するなら、turn 2 へ渡す内容を絞る改修(上記 2)を入れた状態で再評価する。経緯は `ai.constants.ts` の `WEB_SEARCH_TOOL_TYPE` コメントに記録済み。

### 競合 URL — 制約が捏造の抑止として働いた

`competitorRefs` の URL が二次情報ばかり(8 件中 7 件)だったため、turn 1 のプロンプトで 3 パターンを実測した。

| 版                   | 競合数 | URL 実在率 | 内容                                                                 |
| -------------------- | ------ | ---------- | -------------------------------------------------------------------- |
| 指示なし             | 4 件   | —          | 二次情報中心。`backlog.com/ja/` と**別製品を指す誤り**あり           |
| **公式を要求(採用)** | 3 件   | **3 / 3**  | 制作者の公式サイト `suzukigu.me/fatproject/` を発見                  |
| 関連 URL に緩和      | 3 件   | **1 / 3**  | `gamemarket.jp/game/<英語スラッグ>/` と**規則を推測して 2 件が 404** |

**緩めると捏造が増える**という非直感的な結果になった。「公式ページ」 という強い制約があると実際に検索で見た URL を使わざるを得ないが、緩めると「それらしく組み立てる」 余地が生まれる。競合の件数は緩めても増えなかったため、緩める利点が無い。

採用した指示からは、実測で機能しなかった項目(「公式が見つからない場合は similarityNote に申告」= 3 件中 0 件)を外し、「確認できなければその競合は含めなくてよい」 に置き換えた。

**残課題**: 公式を要求しても第三者データベース(`bodoge.hoobby.net`)が 1 件混ざる。構造的な解決は**保存前にコード側で URL の実在を検証する**こと(HEAD で 200 を確認し 404 なら空にする)。AI の遵守に依存しないが、外部リクエストが増えるため本 ADR のスコープ外とした。

### FE タイムアウト → ADR-017 で解消

所要時間は 110 → 88 秒に短縮したが、**FE の `API_TIMEOUT_MS = 55_000` を超えたままだった**。本 ADR の変更で生じたものではなく、PROJECT_STATUS に「53〜113 秒で Vercel Hobby の上限に近い」 と記録済みの既存の積み残しで、**UI からは 504 になっていた**。

**この問題は ADR-017(長時間 AI 処理をキュー無しで非同期化する)で解消した。** POST が 0.66 秒で `202 + jobId` を返すようになり、Vercel の関数実行上限と `API_TIMEOUT_MS` は本機能の制約でなくなった。

なお ADR-017 の実装過程で、本 ADR が導入した**クレジット価格の固定(10cr)が非同期化と噛み合わない経路**が見つかっている(プロセスが落ちると予約行が残る)。詳細と対処は ADR-017 を参照。

## 結果(Consequences)

### 良い影響

- 出荷済みの 2 機能が、同じ変更で同時に直る
- ADR-013 が「差別化価値」と位置づけた機能が、実際に差別化として機能する状態になる
- ADR-015 の無料版 3 軸が、Web Search 抜きでも実質評価を含む構成になる(現行 rubric のままだと実質評価がゼロになる)
- 変更が定数ファイルとプロンプト文字列に限定されるため、レビューと切り戻しが容易

### 悪い影響・リスク

- **過去のスコアと新しいスコアが直接比較できない**。ADR-013 の「履歴比較で相対変化を重視する」設計は、切り替え時点で一度断絶する。UI 上で切り替え時点を示すか、断絶を許容するかは実装時に決める
- 過去レコードの表示ラベルだけが新名称に変わるため、**古い結果を開くと当時と違うラベルで表示される**。キーは同一のため破損はしないが、履歴の見え方は変わる
- 実質評価は記述の評価より**LLM の判断のばらつきが大きくなりうる**。`temperature=0.2` と rubric の点数帯指定は維持するが、再現性は要観測
- 「判断材料が不足している」を返す経路が増えるため、**入力が薄いユーザーの初回体験が厳しくなる**可能性がある。ADR-015 の無料版では改善提案が主役であり、不足の指摘も具体的な要求として返るため許容する

### フォローアップ

- **検証方法**:修正の前後で同一プロジェクトに対しアイデア検証を実行し、提案文を見比べる。1 回 ¥41.65(F23 実測)のため数回で足りる。作文添削が消え、内容への指摘に変わっていることを確認する
- **実装対象**:`apps/api/src/idea-validation/validation.constants.ts` / `apps/api/src/product-diagnosis/diagnosis.constants.ts`(label + criteria)、両 service の `## 採点ポリシー` 文字列、`validation-schema.ts` への「先に確かめるべきこと」フィールド追加、FE の表示
- **着手順序**:ADR-015 の `/check` 実装より**先**に置く。(1) 既存機能が現在も作文添削を返しているため、(2) 修正が安いため、(3) `/check` はこの rubric の上に建つため、先に直さないと同じ欠陥を新機能に複製する
- **監視すべき指標**:同一入力に対するスコアのばらつき(再現性)、「判断材料が不足」判定の発生率
- **見直しトリガー**:実質評価に切り替えてもスコアの再現性が確保できない場合、rubric の点数帯をより機械的な基準(該当項目のチェックリスト化)に寄せることを検討する
