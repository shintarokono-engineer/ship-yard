# ADR-017: 長時間 AI 処理をキュー無しで非同期化する

## ステータス

承認済み(2026-08-31)/ 実装・実測完了(2026-08-31)

## 背景・問題

プロダクト診断(`PRODUCT_DIAGNOSIS`)とアイデア検証(`IDEA_VALIDATION`)は 1 回 **88〜113 秒**かかる。この待ち時間は 2 段の制約を受ける。

```
ブラウザ → Vercel (Server Action) → App Runner (API) → Anthropic
             ↑ 関数実行上限 60 秒        ↑ 制約なし
             ↑ API_TIMEOUT_MS 55 秒
```

- `apps/web/src/app/.../diagnoses/page.tsx` の `maxDuration = 60`(Vercel Hobby の上限)
- `apps/web/src/lib/api/client.ts` の `API_TIMEOUT_MS = 55_000`

**つまり同期実行では UI から完走できない。** さらに悪いことに、FE が 55 秒で fetch を abort しても **API 側は abort を検知しない**。NestJS のハンドラは最後まで走り、`ServiceScore` を INSERT してクレジットも確定する。ユーザーから見た挙動は次のようになっていた。

1. 「実行」を押す → 55 秒待つ → **エラー表示**
2. 裏では 88 秒後に完了し、**履歴一覧には結果が出ている**
3. **10cr は消費済み**

失敗ではなく「結果が届かない」状態で、**出荷済みの差別化機能(ADR-013)が UI から使えていなかった**。

`architecture.md`「非同期処理基盤(キュー)をいつ導入するか」の**トリガー 1(最有力)がまさにこれ**で、同ドキュメントは対処方針まで書いていた。

> 上限に近ければ、キュー導入を待たずに `maxDuration` の引き上げ、または**「実行を投げて結果は後から取得する」形への変更**を検討する必要があります。

関連: ADR-012(クレジット予約)、ADR-013(診断機能)、**ADR-016(本 ADR と同じ作業で発見。rubric とコストの是正)**、`architecture.md` トリガー 1

## 検討した選択肢

### A. キュー無しの非同期化(202 + ポーリング)

- 概要: POST は認可・月次上限・クレジット予約だけを同期で行い `202 + jobId` を返す。AI 実行はレスポンス送出後も継続し、クライアントは進行状態をポーリングする
- 長所:
  - **App Runner は常駐 Node プロセス**なので、レスポンス後も処理を続けられる。キュー(Redis / pg-boss)の導入が要らない
  - Vercel の関数実行上限と `API_TIMEOUT_MS` の両方を**構造的に**無関係にできる(POST は 1 秒未満)
  - 認可とクレジット予約を同期に残せるため、実行できない場合の 403 を即座に返せる
  - 履歴一覧に「実行中」行を出せば、ページを離れて戻っても進行が分かる
- 短所:
  - **App Runner が再起動すると背景処理ごと消える**。ジョブは RUNNING のまま残り、クレジット予約も残る
  - 進行状態を持つテーブルと、ポーリングの実装が増える

### B. Vercel Pro へのアップグレード

- 概要: `maxDuration` を最大 300 秒まで上げられるようにする
- 長所: コード変更がゼロ。確実
- 短所:
  - **月 $20(約 ¥3,000)**。`infrastructure-cost.md` §3.2 C の「Hobby 継続」方針の変更にあたる
  - 収益ゼロの段階で、ADR-016 のコスト削減(1 回 ¥50.1 → ¥27.8)に一晩かけた直後に固定費を積むのは筋が通らない
  - 処理時間が伸びれば再び上限に当たる。**先送りにしかならない**

### C. 所要時間を 55 秒未満に短縮する

- 概要: `WEB_SEARCH_MAX_USES` を削る等で速くする
- 長所: 定数変更のみ。コストも下がる
- 短所:
  - turn 2 は Sonnet が 3,000 トークン以上を生成しており**それだけで 30〜50 秒**かかる。検索を 0 にしても 55 秒を割れない見込み
  - 競合取得数は `competitiveAdvantage` / `marketPotential` の評価根拠そのもので、品質を削ることになる(ADR-016 で検証済み)

### D. キューを導入する(Redis + BullMQ / pg-boss)

- 概要: `architecture.md` が想定していた本来の非同期基盤
- 長所: 再起動耐性・リトライ・排他が最初から揃う
- 短所:
  - 本機能だけのために基盤を入れるのは過剰。`architecture.md` 自身が「**実際に必要になった時点で比較して決める**」としている
  - トリガー 2(メール一斉配信、F21)が**キュー必須**なので、そこで改めて比較するのが自然

## 決定

**A を採用する。キューは導入しない。**

### 処理の流れ

```
POST /workspaces/:slug/projects/:projectId/diagnoses
  ├ 多重実行チェック(RUNNING があれば 409)   … 同期
  ├ 月次上限チェック → クレジット予約         … 同期(失敗なら 403)
  ├ AiJob を RUNNING で作成                    … 同期
  ├ AI 実行を void で切り離す                  … 背景
  └ 202 { jobId } を返す                       … 実測 0.66 秒

GET .../diagnoses/jobs/:jobId  → 進行状態(ポーリング)
GET .../diagnoses/jobs         → 実行中 / 直近失敗(履歴一覧に混ぜる)
```

### 認可とクレジット予約を同期に残す

非同期にすると「実行できません」の 403 を即座に返せず、**ユーザーは待たされた挙げ句に失敗を知る**ことになる。予約を同期に置くことで TOCTOU 対策(ADR-012 の advisory lock)もそのまま効く。

### 進行状態は専用テーブル `AiJob` に持つ

`ServiceScore` / `IdeaValidation` に `status` を足して結果列を nullable 化する案は採らなかった。それらは「**完了した結果**」を表す設計で、履歴一覧・レーダー・前回比較の読み取り側が nullable を前提にしていない。専用テーブルなら**既存の読み取り側を一切変更せずに済み**、1 テーブルで 2 機能を兼ねられる。

一覧の合成規則は次のとおり。

```
一覧 = RUNNING / 直近 24 時間の FAILED のジョブ + 完了した結果 全件
       (DONE のジョブは出さない。結果本体が出るため)
```

完了するとジョブ行が消えて結果行が現れるので、ユーザーには「実行中行が結果行に置き換わった」ように見える。

### 取り残しの回収

App Runner の再起動・デプロイで背景処理が消えると、`status` は RUNNING のまま残る。**`updatedAt` が `AI_JOB_STALE_MS`(20 分)より古い RUNNING は、読み取り時に FAILED へ倒す。**

値は「正常系が絶対に超えない下限」から決めた。各ターンは `ANTHROPIC_REQUEST_TIMEOUT_MS`(180 秒)が上限、リトライ `AI_MAX_RETRIES`(2)を含めて最悪 180 × 2 ターン × 3 回 = 18 分。実測は 88〜153 秒。

**このとき `AiJob.reservationId` を使ってクレジット予約を解放する。** ADR-012 の「予約 → 確定 / 解放」は**同期実行を前提**にしており、プロセスが落ちるとどちらも走らず予約行が `AIUsage` に残ってユーザーの当月枠を食う。同期実行では起こり得なかった経路で、非同期化によって新たに生まれた。

### 多重実行の抑止

同期実行時代は、レスポンス待ちの間ボタンが `pending` で無効化され二重送信が実質的に防がれていた。**即座に応答するようになったことでこの性質が失われる。**連打すれば N 件が並走し N × 10cr が予約される。同一プロジェクト + 同一機能の RUNNING があれば **409 で弾く**(クレジット予約の**前**に確認すること)。

## 理由

- **App Runner が常駐プロセスであることが決め手**。Vercel の Serverless と違い、レスポンス後も処理を継続できる。この 1 点でキュー無しの非同期化が成立する
- **B は先送り**。処理時間が伸びれば再び上限に当たるうえ、収益ゼロで固定費を積む判断はコスト削減の直後としては筋が通らない
- **C は品質を削る**。競合取得数は評価軸の根拠そのもので、かつ turn 2 だけで 55 秒を割れない見込み
- **D は過剰**。`architecture.md` 自身が「実際に必要になった時点で比較」としており、キューが必須になるのはトリガー 2(F21 メール一斉配信)
- **トレードオフの受容**: 再起動時の取り残しは、20 分の staleness 判定 + 予約解放で回収する。完全な再開(ジョブの再実行)は諦める。1 回 ¥27.8・月 30 回上限の機能で、失敗時はユーザーが再実行すれば足りる

## 結果(Consequences)

### 良い影響

- **出荷済みの差別化機能が UI から使えるようになった**(それまで 55 秒で 504)
- POST が **0.66 秒**で返るため、Vercel の関数実行上限が本機能の制約でなくなった
- ページを離れて戻っても、履歴一覧の「実行中」行で進行が分かる
- 既存の履歴一覧・レーダー・前回比較のコードを一切変更していない
- キューを導入していないため、運用対象(Redis 等)も監視項目も増えていない

### 悪い影響・リスク

- **App Runner の再起動でジョブが失われる**。20 分後に FAILED として回収されるが、ユーザーは再実行が必要
- **`findRunning` → `start` の間に競合の窓がある**。クレジット予約は advisory lock で直列化されているが、多重実行チェックは素の SELECT。連打間隔より DB 往復が速いため実害は薄いが、完全な排他ではない。厳密にやるなら status = RUNNING の部分一意インデックスか advisory lock が要る
- **`router.refresh()` がページ全体を再取得する**。一覧は 5 本の API を呼ぶため、10 秒間隔でも 1 回の診断あたり約 45 本になる。`API_URL` に `NEXT_PUBLIC_` を付けない設計(`implementation-rules.md`)のため、クライアントから API を直接叩いて軽くすることはできない
- **完了通知が無い**。別ページにいるユーザーに完了を知らせる仕組みは無く、一覧を開いて初めて分かる
- 参照系(GET)の中で取り残しの UPDATE を行っている。実行頻度が低く N も小さいので許容しているが、増えたら日次バッチへ寄せる

### フォローアップ

- **監視すべき指標**: FAILED になったジョブの発生率(取り残しの頻度)、`reclaimStale` の警告ログ
- **見直しトリガー**:
  - トリガー 2(F21 メール一斉配信)でキューを導入する際、本機能もキューに載せ替えるか比較する
  - 取り残しが頻発するなら、`AI_JOB_STALE_MS` の短縮ではなく**ジョブの再開**(キュー導入)を検討する
  - 同時実行が増えてインスタンスを占有し始めたら `architecture.md` トリガー 4 に該当
- **未対応**: 完了通知(トースト / バッジ)、`maxDuration = 60` の要否見直し(他の Server Action への影響調査が必要)
