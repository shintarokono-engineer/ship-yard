# Spec: 無料公開アイデア検証ツール `/check` と獲得動線

**作成日**: 2026-08-30
**ステータス**: 設計確定(実装計画は writing-plans で別途)
**関連**: ADR-015(本 Spec の出典)/ **ADR-016(rubric を実質評価へ改訂、本 Spec の前提)**/ ADR-013(`IDEA_VALIDATION` の rubric)/ ADR-012(プラン構造)/ ADR-005(AI 戦略)/ ADR-003(テナント解決)/ ADR-002(マルチテナント)/ PROJECT_STATUS §9.12.2 F23

## 0. このドキュメントについて

ADR-015 で決定した「無料公開アイデア検証ツールによる初期ユーザー獲得」を、実装可能なレベルまで具体化します。

### 目的

**LP への訪問がほぼ 0** という状態を解消します。現状の Neorie は「アイデアからリリースまで一元管理する SaaS」という誰も検索しない語で名乗っており、検索・共有される接点を 1 つも持ちません。ログイン不要の単機能ツールを 1 枚公開し、そこを唯一の入口にします。

### スコープの境界

| 区分               | 範囲                                                                                                                    |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| **本 Spec**        | `/check` 公開ページ + 無認証の診断 API + 費用の天井 + 結果ページ + サインアップへの持ち越し                             |
| 非スコープ         | サインアップ後の動線改善 3 件(slug 自動化 / status 駆動の次の一手 / 作成モード追加)。ADR-015 の通り**流入確認後**に着手 |
| 非スコープ         | F23 の有料側コスト是正(`claude-sonnet-5` 化 / `web_search_20260209` 採用)。独立に効くため別タスク                       |
| 非スコープ         | 既存ユーザー向けのツアー / チュートリアル                                                                               |
| **前提(先行実装)** | **ADR-016 の rubric 改訂。`/check` はこの rubric の上に建つため、先に直さないと同じ欠陥を複製する**                     |
| 前提               | Zenn / X による点火(C)。**本 Spec の成果物だけでは流入は立ち上がりません**                                              |

## 1. ブレストで確定した決定事項

| 2   | ログインの要否         | **不要**                                                                | 流入 0 の段階で 6 ステップの壁は致命的                                                                                                     |

| 6   | スコア名               | **「アイデア検証スコア」で有料版と同一**                                | 別名(「言語化スコア」等)は採点対象が文章にすり替わって見え、検索意図との一致を自ら壊す                                                     |

| 8   | 点差への対処           | **事前開示**(「2 軸は Pro で判定。追加するとスコアは変動します」)       | 問題は点の低下ではなく不意打ち。開示で解ける                                                                                               |
| 9   | 出力の主役             | **改善提案**。スコアは併記                                              | 人は自分の点数より、自分のアイデアが良く言語化された文章を貼る                                                                             |
| 10  | モデル                 | **`AI_MODEL_HAIKU`(現行 `claude-haiku-4-5-20251001`)、Web Search なし** | 検索込みでは実費 ¥5 未満に収まる構成が存在しない                                                                                           |

| 12  | 結果 URL               | **推測不能 ID + 既定 `noindex`**、共有は opt-in                         | 他人の未公開アイデアの露出と、薄いコンテンツ大量生成による評価低下を避ける                                                                 |

## 2. 実行経路

### 既存実装との関係

`idea-validation.service.ts` は Day 47.5 で **2-step 化**されています。

- **ターン 1**: `tools: [web_search]` + `tool_choice: 'auto'` で類似プロダクトを調査(Sonnet)
- **ターン 2**: ターン 1 の assistant メッセージ全体を context に含め、`submit_idea_validation` の Tool Use で 5 軸の構造化出力

**公開版は、このターン 2 だけを 3 軸 rubric・Haiku で実行するもの**として実装します。ターン 1 を丸ごと省くことが、そのままコスト削減になります。

rubric は **ADR-016 で実質評価に改訂したもの**を使います(`problemClarity` = 課題の強度 / `targetClarity` = 対象の到達可能性 / `differentiation` = 打ち手の妥当性)。改訂前の rubric を使うと、無料版が採用する 3 軸には実質評価が 1 つも含まれません。

```
[公開版]  ユーザー入力 → ターン 2 相当(Haiku, 3 軸)→ 結果
[有料版]  Project → ターン 1(Sonnet + Web Search)→ ターン 2(Sonnet, 5 軸)→ 結果
```

### rubric の部分適用

`formatValidationRubricForPrompt()` は現在 `VALIDATION_AXES` 全 5 軸を整形します。**軸の配列を引数で受け取れるようにし、公開版は 3 軸だけを渡します。**`VALIDATION_AXIS_RUBRIC` は ADR-016 で改訂済みのものをそのまま参照し、公開版のために別バージョンを持つことはしません(有料版と基準が乖離すると「2 軸を足すとスコアが変わる」という約束が破綻するため)。

ADR-016 で追加する「先に確かめるべきこと」(軸に紐づかない出力)は、公開版でも返します。改善提案と並ぶこの出力が、結果画面を作文添削ではなくアイデア相談として読ませる主要因になります。

`validation-schema.ts` の 3 段防御(JSON Schema / TS バリデーション / `totalScore === breakdown 合計` の整合性アサート)も、対象軸を引数化することでそのまま機能します。**公開版の内部 totalScore は 0〜60 で、100 点への正規化は表示層でのみ行います。**永続化する値も内部値(0〜60)とし、表示のたびに正規化します。二重に正規化された値を保存しないためです。

### 認証・テナントの扱い

公開診断は**テナントが存在しない状態で実行される**ため、既存の前提から外れます。

- `TenantMiddleware` / `WorkspaceGuard` / `ClerkAuthGuard` を通さない専用の controller にする
- `packages/db/src/tenant-extension.ts` の `TENANT_SCOPED_MODELS` は**許可リスト方式**のため、新モデルを追加しなければ `WHERE tenantId = ?` の自動注入対象になりません。公開診断用モデルは**意図的に追加しない**。この意図をコメントで明示する
- `AIUsage` はテナント単位の課金記録であり、公開診断は計上対象外。**費用管理は別系統**(次節)で行う

## 3. データモデル

テナントに属さない新規モデルを 1 つ追加します。

| フィールド          | 型         | 用途                                     |
| ------------------- | ---------- | ---------------------------------------- |
| `id`                | String @id | 推測不能 ID(結果 URL に使う)             |
| `ideaText`          | String     | ユーザーが入力したアイデア文             |
| `totalScore`        | Int        | **内部値 0〜60**(正規化前)               |
| `breakdown`         | Json       | 3 軸の `{ score, comment }`              |
| `suggestions`       | Json       | 改善提案 3〜5 件                         |
| `sharedAt`          | DateTime?  | opt-in 共有された時刻。`null` なら未共有 |
| `claimedByTenantId` | String?    | 持ち越しで登録に至った場合のテナント     |
| `claimedAt`         | DateTime?  | 持ち越し時刻                             |
| `ipHash`            | String     | レート制限の補助キー(生 IP は保存しない) |
| `createdAt`         | DateTime   | 作成時刻                                 |

`ipHash` は生 IP を保存せずハッシュ化して持ちます。個人データの保持を最小化するためです。保持期間の上限(未 claim の結果を何日で削除するか)は未決定事項に送ります。

## 4. 費用の天井

**実装前に必須の計測**: 現行 `IDEA_VALIDATION` を Web Search なし・3 軸で数回実行し、入力 / 出力トークン量を実測します。ADR-015 に記載した **¥2.4 / 回 は未計測の推定値**であり、F23 自身が「着手前に診断を数件実行して実費のばらつきを確認すること」と警告しています。上限値は実測後に決めます。

多層で守ります。

| 層  | 内容                                                             | 目的                                                     |
| --- | ---------------------------------------------------------------- | -------------------------------------------------------- |
| 1   | **日次グローバル上限**。超過後は「本日の枠は終了しました」を返す | **予算の天井をコードで保証する**。これが主防御           |
| 2   | IP ハッシュ単位の時間あたり回数制限                              | 単一の発信元による枠の食い潰しを緩和(回避可能なので補助) |
| 3   | 入力文字数の上限                                                 | 入力トークンによる単価の跳ね上がりを防ぐ                 |
| 4   | `max_tokens` の明示                                              | 出力側の上限を固定する                                   |

日次上限に達したときは、エラーではなく**サインアップ導線を含む案内**を返します。上限は「使えない」状態ではなく「登録すれば今すぐ使える」への転換点として扱います。

## 5. 画面

### `/check`(入力)

Clerk middleware の `isPublicRoute` に `/check` 系を追加します(既存の `/p/(.*)` と同じ扱い)。

- アイデアを書く単一のテキストエリアと実行ボタンのみ。**ログイン導線を前面に出さない**
- ページタイトル・見出し・構造化データを「アイデア評価ツール」として最適化する。狙うのは「アイデア 評価」「ビジネスアイデア 採点 AI」「アイデア 検証 ツール」といった実際に打たれるクエリ
- **このページは index させて育てる**(結果ページとは扱いが逆)

### 結果表示

```
アイデア検証スコア            72 / 100

問題明確性       ████████████░░░░   17 / 20
ターゲット明確性  ██████████░░░░░░   14 / 20
差別化           ████████░░░░░░░░   12 / 20
競合優位性       🔒 Pro で判定します
市場性           🔒 Pro で判定します

※ 2 軸は実際の競合を Web 検索して評価します。
   追加するとスコアは変動します(多くの場合下がります)。

── 改善提案 ────────────────────
[ここが画面の主役。3〜5 件を優先度順に]
```

- **改善提案を画面の主役**に置き、スコアは上部に併記する
- ロック 2 軸は**その場に見せる**。非表示にしない
- 既存の検証結果表示コンポーネント(Day 47 実装)を流用する。3 軸表示とロック行の追加が差分

### 結果 URL

- 推測不能 ID による固定 URL。**既定で `noindex`**
- 共有ボタンは明示的な opt-in(`sharedAt` を立てる)。共有後も `noindex` は維持し、URL を知る人だけが見られる状態にする
- OG 画像にスコアを焼く(X に貼られたときに中身が見える)

## 6. サインアップへの持ち越し

`/check` の結果から登録した人を `/onboarding` に落とすのは最悪の設計です。**アイデア文が手元にある以上、全部作ってしまいます。**

```
結果ページ「競合優位性と市場性も見る」
  → Clerk サインアップ(結果 ID を短命トークンで保持)
  → ワークスペース自動作成
  → ideaText から Project(status = IDEA)を自動作成
  → 5 軸フル診断を自動実行
  → 結果ページに着地
```

- 引き継ぐのは**結果 ID のみ**。アイデア文は公開側に保存済み
- トークンは短命かつ 1 回限り。`claimedByTenantId` / `claimedAt` で二重引き換えを防ぐ
- フル診断は AI クレジットを消費するため、トライアル付与後に実行する。**クレジット不足時は診断を実行せず、プロジェクトだけ作って結果ページに導線を置く**(失敗で着地させない)
- ワークスペース自動作成の slug は ADR-003 の「URL 共有時の摩擦を最小化」と衝突しうる。**本 Spec では自動生成とし、設定画面で改名可能にする**。ただし公開 LP を持つワークスペースの改名制約(§9.5 の link 切れ)は、動線改善タスク側で扱う

## 8. 本 Spec と独立して効く関連タスク(F23)

有料側の赤字(実測 ¥6.94/cr > 損益分岐 ¥4.93/cr)は本 Spec とは別に解消できます。ADR-015 の「フォローアップ」に詳細。

1. `AI_MODEL_SONNET` を `claude-sonnet-4-6` → **`claude-sonnet-5`**($3/$15 → $2/$10、同一トークン量で ¥41.65 → 約 ¥31)
2. `WEB_SEARCH_TOOL_TYPE` を **`web_search_20260209`** へ(動的フィルタリングが 67,831 トークンへの膨張を抑える。**F23 の本命**)
3. `WEB_SEARCH_MAX_USES` を 5 → 2

`ai.constants.ts:262-268` のコメント(「`web_search_20260209` は code_execution tool の有効化が必須」)は現在の API 仕様と一致しないため、併せて訂正します。
