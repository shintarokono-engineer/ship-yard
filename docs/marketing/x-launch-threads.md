## 書くときの前提(重要)

- **ユーザー数・導入実績・利用者の声は書かない。** 実ユーザー 0 の段階で数字や証言を出すと景品表示法の優良誤認に当たりえます。書けるのは「作ったもの」「作った過程」だけです
- 「初リリースです」は 1 度しか使えない強いカードなので、リリース当日のスレッド 1 本目に集中させます
- 文字数は X の全角換算(全角 1 文字 = 2 weight、上限 280 weight = **全角 140 字**)。各案の末尾に概算字数を付けています

## 単発ストック(リリース後に小出しする用)

1 日 1 本ペースで放流できる粒度にしてあります。スレッドと違い、それぞれ単体で完結させています。

**S1(設計の話)**

> マルチテナントで `WHERE tenantId = ?` を書き忘れる事故は、Prisma Client Extension で自動注入して構造的に潰しています。
>
> raw SQL には効かないので、そこは ESLint のカスタムルールで検出。注意力に頼る設計をやめると夜よく眠れます。

約 112 字

**S2(AI 課金)**

> AI の課金をトークン従量のまま見せると「押していいのか」がわからないので、クレジット制にしました。
>
> Haiku 1 cr / Sonnet 3 cr、実行ボタンの横に「残り 273 cr」と出す。原価とユーザー体験の折り合いはここが落としどころでした。

約 109 字

**S3(同時実行)**

> AI クレジットの上限判定、素直に書くと「集計 → 確認 → 実行」の間に別リクエストが入って両方通ります。
>
> 対策は在庫引当と同じで、実行前に予約行を INSERT。テナント単位の advisory lock で直列化しています。

約 99 字

**S4(Stripe)**

> チーム課金の人数同期は、DB コミット後に Stripe を更新する Saga にしています。
>
> 失敗してもユーザー操作は成功扱い。同じ数量を何度送っても結果が変わらない冪等な API なので、あとからいくらでも直せます。

約 98 字

**S5(運用)**

> ローカルも CI も通るのに本番だけ壊れる、で溶かした時間の犯人は環境変数でした。
>
> Vercel と Secrets Manager は互いに読めず、反映方法も違う。追加先の判断フローをドキュメントに書いて、機械的に確認するようにしました。

約 105 字

**S6(RAG の透明性)**

> RAG の検索結果には「運営が用意したサンプル由来か」のフラグを持たせて、UI に出しています。
>
> 他人のプライベート文書は絶対に混ぜない設計なので、何を参照したかを隠さないことがそのまま信頼になると思っています。

約 102 字

**S7(プロダクト寄り)**

> Neorie のアイデア検証、GO だけでなく PIVOT と NO_GO も普通に返ってきます。
>
> 自分のアイデアで試したら容赦なく刺されたので、そのまま方向を変えた機能もあります。作り始める前に殴ってもらうのは、思ったより効きます。

約 104 字

**S8(開発プロセス)**

> 設計判断は全部 ADR に残しました。現時点で 14 本。
>
> 「なぜこうしたか」が残っていると、3 週間後の自分が同じ議論を繰り返さずに済みます。個人開発でも ADR は元が取れました。

約 83 字
